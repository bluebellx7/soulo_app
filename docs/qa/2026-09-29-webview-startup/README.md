# WebView 首次打开实测（2026-09-29）

用户反馈上一版只增加备用 WebView 后没有明显变快。本次实际启动模拟器，先测上一版，再根据分段计时修复瓶颈并复测。数据见 [measurements.json](measurements.json)，复测脚本见 [benchmark_webview_startup.py](../../../scripts/benchmark_webview_startup.py)。

## 条件和口径

- iPhone 17 Pro / iOS 26.2 模拟器，Debug，同一台 Mac；每轮终止并重新启动 App，模拟器系统保持启动。
- 每个自动化分组 3 次，预热开关按轮次交替顺序；测量期间不并行编译或运行测试。
- 通过现有 `soulo://open?url=…` 路由进入正常搜索流程；从 `search_submit` 到现有页面就绪桥接信号 `content_visible` 计时，不是完整页面下载耗时，也不是像素级首屏测量。
- “等待 2.5 秒”指 `pool_activate` 后再等待 2.5 秒；“快速进入”指再等待 0.1 秒，实际提交还包含系统 URL 路由耗时。
- 本地页面固定 HTML、无外部资源、HTTP `no-store`；真实搜索为 Bing 的 `swift` 查询，受网络与网站缓存影响。
- 使用模拟器中已下载的默认订阅；合并规则约 58 MB，订阅原始档案约 82 MB。最终版本的派生缓存事先生成，然后进行进程冷启动测试。这里没有把首次安装/升级后的缓存生成成本算成零。
- 旧版本本地快速进入的首个关闭预热样本遇到系统首次打开确认，已标为无效；本文引用的开启预热分组及 2.5 秒分组未受影响。

## 结果

以下是开启预热时的 3 次中位数，比较上一版只预热 WebView 与本次完整优化：

| 场景 | 上一版 | 本次 | 耗时下降 |
| --- | ---: | ---: | ---: |
| 本地页面，等待 2.5 秒 | 4848.0 ms | 1645.2 ms | 66% |
| Bing 搜索，等待 2.5 秒 | 6795.3 ms | 3000.8 ms | 56% |
| 本地页面，快速进入 | 3687.8 ms | 2374.7 ms | 36% |

本次同一二进制内，只切换备用 WebView 的 A/B：

| 场景 | 关闭预热 | 开启预热 |
| --- | ---: | ---: |
| 本地页面，等待 2.5 秒 | 2263.4 ms | 1645.2 ms |
| Bing 搜索，等待 2.5 秒 | 3649.4 ms | 3000.8 ms |
| 本地页面，快速进入 | 2360.7 ms | 2374.7 ms |

快速进入时经常来不及建立备用 WebView，预热本身没有可靠收益；改善来自规则准备与缓存。等待预热完成后，备用 WebView 在本次测试中再减少约 0.6 秒。

手动重启 App，从首页打开已保存的 Bing 任务标签，确认初始 `load_requested=pending`，开启时 `pool_hit=ready=true`，页面实际显示正常。各一次的 `acquire_start → content_visible` 为关闭预热 3167.5 ms、开启预热 2361.8 ms。这是最终版本内的单次路径验证，起点不含点击/切换动画，不能与上表直接横向比较或视为稳定统计结论。

## 瓶颈与修复

1. **首次页面同步生成广告隐藏脚本。** 上一版运行时安装约 1.6 秒。本次提前在后台准备，持久化派生脚本；最终等待 2.5 秒分组运行时安装约 46 ms。
2. **每次进程启动重复遍历、编码大型规则。** 缓存原生规则标识，启动时直接查询 WebKit 已编译规则。缺少任一编译产物时回退完整生成，不返回部分规则。
3. **延迟订阅检查与搜索相撞。** 服务初始化会在主线程读取、合并大型订阅档案，即使当天已检查过。本次在真正执行前再次判断搜索状态，并用经过验证的档案元数据跳过无须更新的初始化；到期、文件变化、解析器变化、空规则、迁移覆盖均走原检查路径。
4. **预编译白名单签名与页面安装路径不一致。** 统一使用加入兼容站点后的有效白名单，避免重复准备。

派生缓存只有两个固定文件，原子替换；键包含构建身份、规则版本、档案大小和修改时间、内置覆盖、白名单及脚本模式。损坏或过期时重建。备用池保持最多一个空白实例；隐私模式独立数据存储，扩展专属配置不复用通用备用实例；后台与内存警告释放备用实例。

首次构建派生缓存仍有成本。本次预备运行记录：后台脚本生成约 1.70 秒、原生规则准备约 6.59 秒、首次订阅验证约 2.57 秒，部分阶段并发。升级、规则变更或系统清理缓存后可能再次发生；这些情况不能保证与缓存命中后的数字相同。模拟器数据也不代表真机耗时。

## 复现

安装 Debug 构建到专用模拟器，先正常启动并等待规则准备完成、处理首次外部链接确认，然后运行：

```sh
python3 scripts/benchmark_webview_startup.py --device <UDID> --repeats 3 --output /tmp/soulo-local
python3 scripts/benchmark_webview_startup.py --device <UDID> --repeats 3 --delays 2.5 --url 'https://www.bing.com/search?q=swift' --output /tmp/soulo-bing
```

脚本会反复终止该模拟器上的 Soulo，应使用测试模拟器。默认本地 HTTP 场景通过启动参数关闭 HTTPS 自动升级，仅作用于测试进程。`SOULO_BROWSER_TRACE=1` 和 `SOULO_DISABLE_WEBVIEW_WARMUP=1` 仅 Debug 生效；Release 不记录这些事件、不开放关闭预热开关。计时日志不输出用户网址或查询内容。

## 回归验证

已构建成功，并运行 200 项相关测试。首次完整运行发现新增缓存测试中的 2 个断言失败：复用 URL 对象读取文件属性时可能命中系统缓存，无法观察到原子替换或删除。现已在读取前清除 URL 属性缓存；修复后重跑缓存和订阅的 19 项测试，全部通过。其余 181 项在完整运行中通过，最终 200 项均有通过记录。

覆盖备用池复用/释放/隐私隔离、派生缓存损坏与失效、缺失 WebKit 编译产物回退、广告订阅、实际请求拦截、手动广告屏蔽、标签恢复、扩展生命周期及 WebViewModel。`git diff --check` 与脚本语法检查通过。测试摘要见 [validation.txt](validation.txt)。

三轮性能数据采集后补充的最后一个修复仅刷新 URL 文件属性缓存；性能采样时生产调用本来就在创建新的 URL 对象。该修复已重新构建并完成上述定向回归，未把重复性能采样混入已记录的三轮统计。
